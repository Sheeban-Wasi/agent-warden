# PRD: Agent-Warden (Open Source Middleware for AWS Strands)

## 1. Executive Summary

**Agent-Warden** is a security-first middleware library designed specifically for the **AWS Strands Agents SDK**. It acts as a "Sentinel" layer that intercepts agent thoughts and tool calls to prevent destructive SQL operations, redact PII, and enforce permission boundaries. It is built to be the "Pydantic of Agent Security"—un-opinionated, zero-dependency where possible, and audit-ready.

## 2. Target Persona & Problem

* **Persona:** Software Engineers at regulated enterprises (Finance/Insurance) building on AWS Strands.
* **The Problem:** Current agent safety relies on "vibe coding" (Regex or system prompts), which fails against sophisticated exploits and fails compliance audits.

---

## 3. Core Feature Specifications

### Feature 1: `warden-sql` (AST-Based Query Guard)

* **Requirement:** Must block destructive SQL commands using Abstract Syntax Tree (AST) parsing rather than Regex.
* **Technical Spec:**
* Integrate `sqlglot` for cross-dialect SQL parsing.
* **Input:** Raw SQL string generated by the LLM.
* **Logic:** Traverse the AST to identify node types.
* **Default Blocklist:** `Drop`, `Alter`, `Truncate`, `Delete`.
* **Modes:** `read-only` (Allow only SELECT), `safe-write` (Allow INSERT/UPDATE to specific tables), `strict`.
* **Success Metric:** Block `"EXEC('DR' + 'OP TABLE users')"` which standard Regex fails to catch.



### Feature 2: `warden-pii-proxy` (Context-Aware Redaction)

* **Requirement:** A lightweight wrapper for Strands models that redacts sensitive data (Email, SSN, API Keys) before it reaches the LLM.
* **Technical Spec:**
* Use high-precision NER (Named Entity Recognition) combined with specialized patterns.
* **Synthetic Swapping:** Replace "John Doe" with `[PERSON_1]` instead of `[REDACTED]`. Maintain this mapping throughout the session context.
* **AWS Integration:** Support for `AWS Comprehend` as an optional backend for enterprise-grade detection.



### Feature 3: `warden-permissions` (Capability Scoping)

* **Requirement:** Force agents to operate under a "Manifest" of allowed tools, preventing "Goal Hijacking."
* **Technical Spec:**
* **Manifest System:** A `warden_manifest.yaml` that defines what tools an agent can call.
* **Enforcement:** Intercept the `Strands` tool-calling loop. If an agent tries to call `delete_s3_bucket` but it's not in the manifest, raise a `PermissionDeniedError`.
* **Identity Delegation:** Pass-through headers to ensure the agent inherits the "Least Privilege" of the calling user.

## 4. Technical Architecture for the "Moat"

To ensure this becomes an industry standard, the agent should build following this "Moat" architecture:

| Component | Logic | Moat Value |
| --- | --- | --- |
| **The Interceptor** | Middleware that hooks into the `Strands` event loop (Pre-Tool Call / Post-LLM Gen). | Deep integration makes it "sticky" and hard to replace. |
| **The Audit Vault** | A `trace_decision()` function that logs *why* a query was blocked in JSON (e.g., `{"reason": "AST_FORBIDDEN_NODE", "node": "Drop"}`). | Banks buy this for compliance; it's the "Product" they actually need. |
| **Zero-Trust Bridge** | A secure bridge for **AWS Strands** that ensures no tool call is executed without a Warden signature. | Positions the library as the "Official-Unofficial" security standard for Strands. |

## 6. Constraints & Safety

* **Naming:** Avoid using "AWS" or "Amazon" in the package name (use `agent-warden`).
* **Performance:** Middleware must add `< 50ms` latency to the agent loop.
* **Reliability:** "Fail-Closed" philosophy. If the parser crashes, the query must be blocked by default.
